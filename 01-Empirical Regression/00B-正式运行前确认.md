# 正式运行前确认

本文件供 `02`—`08` 模块共同使用。任何正式估计开始前，必须向用户确认本轮方案；在用户确认前，不运行回归或其他估计程序。

## 路径解释规则

- `能力包根目录`固定指 `ENTRY.md`、00A—00D 所在目录；阶段 Skill 中的“读取 00A/00B/00C”均指读取能力包根目录中的对应文件。
- `AI-Work` 固定指项目 `Inf/00-项目总说明.md` 登记的真实绝对路径，不从当前工作目录猜测。
- 阶段代码文件固定指当前阶段 `SKILL.md` 同目录下的 `编号-中文名称代码.md`。
- 所有相对输出路径以本轮阶段 Temp 目录为工作目录解析；不得以能力包目录、数据目录或 PowerShell 当前目录解析。

## 项目文件位置

以下路径均以用户在 `01-int` 中指定的 `AI-Work` 为根目录：

- 项目总控与进度：`AI-Work/Inf/00-项目总说明.md`；
- 项目信息：`AI-Work/Inf/01项目信息.md`；
- 数据索引：`AI-Work/Inf/02数据索引.md`；
- 用户确认的每轮方案：`AI-Work/Plan`；
- 试跑代码、日志、临时表图和完整尝试结果：`AI-Work/Temp/编号-中文名称`；
- 用户确认采用的正式代码：`AI-Work/Reg`；
- 用户确认采用的正式结果：`AI-Work/Result`。

例如项目根目录若为 `D:\项目\AI-Work`，用户方案写入 `D:\项目\AI-Work\Plan`，不得写入 `Temp`；运行中产生的文件写入对应的 Temp 子目录，不得写入本能力包源目录。

## 一、确认方式

先读取项目 Inf、已确认的正式代码与结果，并从当前模块判断哪些信息已经明确。只向用户确认缺失、存在多种口径或将影响本轮估计的内容，不要求用户重复已经给出的信息。

向用户提交一张“本轮方案确认卡”，在同一条消息中列完本轮所有待确认字段；字段多时可在同一张卡内分组，但不得拆成逐个变量的连续提问。用户只回答部分字段时，下一次只列仍缺失或互相矛盾的字段，不重复已确认项。

## 二、公共确认卡

不适用的项目明确写“不使用”。变量名必须用数据索引、数据元信息或已运行代码核实，不得把变量标签、论文概念或旧代码中的近似名称直接当作准确变量名。

### 1. 估计目标

- 当前实证方法与本轮模块；
- 本轮要回答的问题；
- 目标估计量或结果对象，例如系数、ATE、ATT、LATE、动态效应、断点局部效应、预测结果、结构参数或风险比；
- 用户预期的方向；没有方向要求时写“无”。

### 2. 变量

- Y：被解释变量或结果变量，可包含多个候选口径；
- X/T/D：核心解释变量、处理变量、DID、剂量或冲击变量；
- Controls：基准控制变量、必须保留项、可替换或可组合项；
- M：机制或中介变量；
- IV：工具变量及对应的内生变量；
- Z：调节、分组或异质性变量；
- Weight：抽样权重、人口权重、匹配/平衡权重或其他权重；
- 当前方法需要的其他变量。

### 3. 数据、样本与推断

- 使用的终版数据文件；
- 观察层级、面板个体和时间变量；
- 样本期、样本限制和基准样本；
- 固定效应或其他吸收项；
- 聚类层级、稳健协方差、Bootstrap、随机化推断或其他推断方式；
- 随机种子、重复次数或折数（适用时）；
- 已知的数据处理：缩尾、插值、标准化、对数、滞后、缺失处理等。

## 三、方法附加确认

当前编号模块只显示当前方法实际需要的附加项目，不得把以下清单全部抛给用户。尚未在具体模块配置的方法附加项不得凭空补造。

- DID：处理组、首次处理时间、对照组、是否分期实施、是否允许处理逆转、事件窗口和基准期；
- IV：内生变量、excluded instruments、相关性依据、排除限制和目标 LATE/参数；
- RDD：运行变量、阈值、sharp/fuzzy/kink、带宽与局部样本；
- SCM/SDID：处理单位、处理时点、donor pool、预测变量和前后期；
- 匹配/重加权：处理前协变量、目标 ATE/ATT/ATC、共同支撑和权重规则；
- RCT：随机化单位、分层/阻断、处理分配、依从性、失访和 ITT/TOT；
- 因果机器学习：Y、T、X、W、可选 Z、目标 ATE/CATE、学习器和验证方案；
- 时间序列：时间索引、频率、季节性、预测或动态解释目的；
- 空间计量：空间单元、坐标/边界、权重矩阵及其标准化；
- 结构估计：主体、状态、行动、参数、均衡/决策规则、矩条件/似然和反事实；
- 生存/流行病学：time origin、duration、event、删失、风险集、竞争风险和效应尺度。

## 四、依赖与代码预检

在提交方案确认卡前完成只读预检，不运行模型：

1. 从用户选中的代码段列出全部 Stata 外部命令、Python import 或 R package；
2. Stata 用 `which`，Python 用独立 `import`，R 用 `requireNamespace(..., quietly=TRUE)` 检查；
3. 将“已存在／缺失／版本无法确认”逐项写入确认卡；
4. 依赖缺失时只允许用户在确认卡中选择：安装该依赖、跳过该检验、改用代码库中已经存在的替代检验；不得运行到一半再静默安装；
5. 用户授权安装时，把依赖名称、来源、安装命令和授权内容写入 Plan，安装日志保存到本轮 Temp。安装失败只把该检验标为“受阻”，其余无依赖检验继续执行。

复制代码到 Temp 后，运行前必须完成占位符门禁：

1. 在 Plan 中建立“模板占位符 → 准确值”表；
2. 替换所有可执行行中的中文占位符和示意名称，包括但不限于以“用户”“当前”“终版”“处理单位”“处理年份”“变量列表”“控制变量”“fe_list”“cluster_id”“user_”开头或结尾的内容；
3. 对所有实际变量运行 `confirm variable` 或对应语言的列名检查，对所有输入文件运行存在性检查；
4. 逐行复核 do-file/脚本；任何未替换占位符、未定义宏、伪函数（例如 `user_defined_objective`）或仅作示意的变量名仍存在时，禁止启动引擎；
5. 把预检结果写入 `00-执行状态.md`。只有“占位符=0、缺失变量=0、缺失输入=0、未处理依赖=0”时才允许运行该代码段。

## 五、显著性底线与诊断标准

要求用户选择本轮目标结果判断“达到要求”的最低标准：

- 一颗星：`p < 0.10`；
- 两颗星：`p < 0.05`；
- 三颗星：`p < 0.01`；
- 或用户另行指定标准。

显著性底线是目标结果的筛选与汇报标准，不得伪造、修改或隐瞒结果。对置信区间、预测误差、结构参数或其他不适合星级的对象，必须让用户在确认卡中写明可机械判断的标准，例如“95% CI 不含 0”“测试集 RMSE 小于 0.20”“参数位于 [a,b] 且优化成功”；用户没有给出数值或布尔判据时，目标结果状态只能写“未设底线／无法判断”，不得由 AI 自行补标准。

星级只适用于用户关心的目标系数。诊断性检验必须逐项记录：检验目的、原假设、统计量、p 值或临界值、适用条件以及结论。平衡、平行趋势、密度、欠识别、弱识别、过度识别、单位根、残差白噪声、空间相关、比例风险、模型收敛等不能统一解释为“越显著越好”。

## 六、未达到底线时的处理方式

让用户在正式运行前选择：

1. **先跑确认方案**：先运行当前主方案；若未达到底线，再由用户决定是否广泛尝试。
2. **直接授权广泛尝试**：在用户预先圈定的范围内连续尝试，并完整汇报。
3. **不做额外尝试**：只报告确认方案的实际结果。

如果选择广泛尝试，逐项确认允许的范围：

- 多个 Y、X/T、M、IV、Z 或权重口径；
- 控制变量替换名单、必须保留项和组合上限；
- 允许缩尾、插值或变换的变量、阈值和方法；
- 允许删除、替换或增加的固定效应；
- 允许调整的聚类或推断方式；
- 允许调整的样本期、地区、行业、特殊年份和尾部样本；
- 当前模块允许的其他估计量、带宽、滞后、权重矩阵、学习器或数值设定。

不得越过用户确认的搜索范围。缩尾、插值和变量变换必须生成新变量，不覆盖原变量。删除固定效应、改变样本、估计对象或识别设计时，必须明确说明改变了什么，不能只把它当作显著性按钮。

## 七、完整汇报和四种状态

每轮结果汇报必须记录：

- 当前方法、模块、Plan 编号和准确路径；
- 代码、输入数据、运行引擎和版本、外部命令及版本、随机种子；
- estimand、实际变量、样本限制、变量处理、FE、聚类或其他推断；
- 核心估计、标准误、置信区间、p 值/星级、N 和样本变化；
- 每项诊断的目的、原假设、统计量、p/临界值、适用性和结论；
- 退出码、完成标记、日志核验、警告、共线性删除、样本损失、收敛和输出文件完整性；
- 下列四种状态：

1. **运行状态**：成功、部分成功、失败或未运行；
2. **方法诊断状态**：通过、未通过、不适用或无法判断；
3. **目标结果状态**：是否达到显著性底线和方向要求；
4. **采纳状态**：待用户确认、已采纳或未采纳。

审稿回复或质询任务另加一项**任务回应状态**，不得被上述四种技术状态替代：`已完成`＝现有结果足以回应质询；`待完成`＝仍需数据或检验；`暂无法完成`＝已经检验，但结果不能支持当前论断。代码运行成功或机制检验跑完，不自动等于审稿任务已完成。

广泛尝试必须汇报所有已运行规格，包括未达到底线、方向不符和运行失败的规格；可以另外汇总达到要求的规格，但不能只展示通过结果。

普通单次运行不强制创建单独的规格台账。只有用户授权广泛尝试、多规格循环、规格曲线、模型比较或其他需要机器可读汇总的任务，才在当前模块 Temp 中创建规格台账。

规格台账每个计划规格占一行，至少记录规格编号、Plan、变量、样本、变换、FE、cluster、方法设定、N、估计、SE、CI、p、底线状态、诊断状态、`_rc`、警告、运行状态和采纳状态。所有失败和不显著规格必须保留。

只有长耗时、批量、Bootstrap、安慰剂、机器学习、结构估计、测速或用户要求时创建运行计时 CSV；记录开始/结束、墙钟秒数、退出码、完成标记、成功/失败数和超时状态。

## 八、方案落盘

用户确认后，把本轮方案写入 `AI-Work/Plan`，不得写入 `Temp`。

编号规则：

1. 只检查 `AI-Work/Plan` 直接目录下以连续数字开头的方案 Markdown；
2. 没有既有方案时从 `01` 开始；
3. 已有方案时取当前最大编号加一；
4. 文件名使用 `NN-模块编号-中文名称-方案.md`，例如 `01-02-基准回归-方案.md`；
5. 用户后续修改同一模块方案时，新建下一个编号并注明替代哪个旧方案，不覆盖或重编号旧文件。

方案文件记录：确认时间、当前方法、模块、用户要求、估计对象、变量、数据与样本、固定效应、推断方式、显著性底线、方向要求、尝试模式、授权搜索范围、运行引擎以及对应的 Temp 子目录。

方案落盘后，才在 `AI-Work/Temp/模块编号-中文名称` 中编写和运行本轮代码。代码、日志、临时表图、规格台账和结果汇报均注明对应的 Plan 编号。

## 九、执行状态、检查点与中断恢复

每轮方案落盘后、运行任何模型前，必须在本轮阶段 Temp 创建或更新 `00-执行状态.md`。固定字段为：

```text
Plan编号：
阶段编号与名称：
当前方法：
本轮代码：
本轮选定检验：
依赖预检：
占位符/变量/输入预检：
每项检验状态：待运行｜运行中｜成功｜失败｜受阻｜用户跳过
每项检验的代码、log、输出和结果位置：
最后成功检查点：
最后错误：
下一项动作：
最后更新时间：
```

强制执行顺序：

1. 创建状态文件后，完整读取项目 `AI-Work/Inf/00-项目总说明.md`，把本阶段标为“进行中”，写明 Plan 和状态文件绝对路径；保存后再次完整读取确认。
2. 启动某项检验前，把该项改为“运行中”并保存。
3. 每完成一项检验或一个批次，立即写入成功/失败/受阻状态、代码、log、输出、错误和下一动作；不得等全部检验结束后一次补写。
4. 每个检查点写完后，完整读取项目进度锚点，更新阶段状态和最后成功检查点，保存后再次完整读取确认。
5. 任务中断或新 AI 接手时，依次完整读取项目进度锚点、最新 Plan、`00-执行状态.md`、状态文件列出的代码/log/输出；从第一项非终态检验继续。已经“成功”且输出存在的项目不重跑；状态写“成功”但输出缺失时改为“失败”，并把“重新运行该项”写入下一项动作。
6. 只有本轮所有选定检验都进入“成功／失败／受阻／用户跳过”之一、结果汇报已写入且进度锚点已复读确认，阶段才可结束。只要存在“待运行／运行中”，不得宣告完成。
7. 某项失败或受阻时，先把直接依赖该项输出的后续检查标为“受阻”；不依赖它的检查继续执行。所有独立检查进入终态后，再一次性向用户报告错误、已尝试处置和需要的决定，不因单项错误丢弃整轮其余工作。
8. 阶段状态按固定规则写入进度锚点：全部选定检查成功＝“已完成”；至少一项成功且同时存在失败、受阻或用户跳过＝“部分完成”；没有成功且存在失败或受阻＝“受阻”；全部为用户跳过＝“部分完成（用户跳过全部检查）”。不得使用其他近义状态。

## 十、正式采用

所有开发、调试、失败运行和候选结果保留在 Temp。只有用户明确确认采用后，才：

1. 将整理后的最终代码复制到 `AI-Work/Reg`；
2. 将采用的表格、图形、结果文件和结果说明复制到 `AI-Work/Result`；
3. 在正式文件中注明来源 Plan 编号和 Temp 版本；
4. 不删除或覆盖 Temp 中的历史尝试。

正式文件使用 `Plan编号-阶段编号-中文名称-内容` 命名；目标文件已存在时追加 `-v02`、`-v03`，不得覆盖。复制后对比文件大小或哈希，确认 Reg/Result 与被采纳的 Temp 来源一致。
